---
description: 失敗しているテストを実行し、テストが完全に通るまで自律的に実装と修正を繰り返す
---

対象のコンポーネントやロジックについて、以下のステップを人間に許可を求めず自律的に実行してください。

1. テストコマンド（`npx vitest run <パス>`）を実行し、エラーログを読み取る。
2. テストをパスさせるために必要な実装コードを、厳格な型定義とエラーハンドリングを用いて記述する。
3. 再度テストを実行し、失敗した場合はログを分析して自己修正する。これを「すべてのテストがパスするまで」繰り返す。
4. 全てパスした場合、コードのクリーンアップ（リファクタリング）を行い、完了を報告する。

---

## ⚠ `npm run test` を使わない

このリポジトリの `npm run test` は **`vitest`（watch モード）で、終わらない。**
自律ループから呼ぶと**そこで固まる**。必ず単発実行を使う。

```bash
npx vitest run <パス>     # 絞って回す（速い。ふだんはこれ）
npm run test:run          # 全部（vitest run）
npm run verify            # 最後に通し（lint → test → build）
```

## 2 で書くもの

- **`any` を使わない。** 逃げ道が要るなら `unknown` + 絞り込み
- **純粋な計算は `src/features/<domain>/lib/` へ。** コンポーネントの中や
  隣の `utils.ts` に書かない（`lib/` に置くとテストが書けるようになる）
- **保存は【楽観的に画面を変える → 保存 → 失敗したら戻す → 成功してから
  履歴に積む】。** 立ち位置の編集は `features/scene/hooks/usePositionCommit` を通す
- **Supabase のエラーは `src/lib/supabase/errors.ts` の `toUserMessage`** を
  通して、`useUIStore` の `showToast` で出す
- 文言は ja / en / ko の3つ。色と余白はトークン経由

詳しくは [.claude/rules/](../rules/README.md)。

## 3 のループで、やってはいけないこと

**テストを通すために、テストの方を緩めない。**

- 期待値をコードの出力に合わせて書き換える
- `it.skip` にする / assert を消す
- `try {} catch {}` で例外を握り潰す
- 型を緩める（`as` で押し通す、`any` を入れる）

これをやると、**テストは緑になるが何も守られていない**状態になる。
仕様の方が間違っていると判断したなら、**手を止めて user に言う**。
勝手にテストを書き換えない（それは仕様変更）。

**同じ場所を3周しても通らなければ、そこで止めて報告する。**
何を試して何が起きたか、いま何が分かっていないかの2つを書く。

## 4 のクリーンアップ

**通った直後にやる。** ただし範囲を絞る:

- 重複の除去、命名、コメント（**なぜそうしたか**を残す）
- **挙動は変えない。** 変えたくなったらテストの側から始める（0 に戻る）
- 大きく割るなら `/refactor`（あちらは事前調査から始まる）

**クリーンアップの後、もう一度テストを回す。** 通ったのを確認してから報告する。

## 出す前に

```bash
npm run verify
```

画面に見える機能を足したなら、コミット前に `/qa-checklist`。
