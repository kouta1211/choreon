ユーザーから機能要求（一言のアイデアなど）を受け取ったら、**途中で一切人間に確認を求めず**、以下のステップを最後まで自律的に一気通貫で実行してください。

1. **[/branch 相当]** 要件から適切な英語ブランチ名（例: `feat/xxx`）を生成し、`git checkout -b` を実行する。
2. **[/spec 相当]** プロジェクトの既存文脈を読み込み、`docs/features/` 配下に詳細な仕様書ファイルを作成・保存する。
3. **[/test-gen 相当]** 仕様書に基づき、`any` を排除した厳格なテストコード（`xxx.test.tsx` 等）を作成する。
4. **[/test-pass 相当]** テストを実行し、すべてのテストがパスするまで実装コードの作成と自己修正を繰り返す。
5. **[/qa-checklist 相当]** 画面に見える変更なら、実機の台本（`docs/qa-checklist.html`）へ項目を足す。
6. **[/commit 相当]** 変更差分を分析し、このリポジトリの作法に従ったメッセージで `git add` および `git commit` を実行する。
7. **[/pr 相当]** `git push origin HEAD` を実行し、変更理由をまとめたプルリクエスト（`gh pr create`）を作成する。
8. **[/wrap-up 相当]** 今回の試行錯誤で得られた教訓を `docs/lessons_learned.md` に追記して永続化する。

全工程が完了したら、「✅ すべての工程（仕様策定〜PR作成〜学習完了）が完了しました！ PRのURL: <URL>」と最終報告を行ってください。

## 指示から変えたこと

| 変えた所 | なぜ |
| --- | --- |
| `docs/02_features/` → **`docs/features/`** | 前者は存在しない。初回で失敗する |
| Conventional Commits → **このリポジトリの作法**（日本語・プレフィックス無し） | 全履歴がそう揃っている。混ぜると2種類になる（`/commit`） |
| **5 に qa-checklist を挿入** | `CLAUDE.md` の決まり。**画面に見える変更はコミット前に台本へ足す**。飛ばすと、user が実機で確認できない機能が出荷される |
| 「[/reset 相当]」 → **[/wrap-up 相当]** | 書いてある中身は wrap-up の仕事。`/reset` は畳む前の安全確認 |
| 最終報告から `/clear` の案内を削除 | PR は**まだマージされていない**。畳むかどうかは、user が PR を見てから決める |

## 止まる条件（**ここが本体**）

一気通貫は、**間違った前提の上に6工程を積み上げる**という失敗の仕方をする。
最初の分岐で誤ると、テストも実装も PR もその誤りに沿って正しく作られてしまい、
**全部を捨てることになる**。だから止まる所を決めておく。

**次のどれかに当たったら、そこで止めて報告する。先へ進まない。**

1. **作業ツリーが汚れている / `main` 以外に居る**（工程1の前）
   … 巻き込む。`git status --short` と `git branch --show-current` を先に見る
2. **DB のスキーマ変更が要る**（`supabase/schema.sql`・GRANT・RLS）
   … 取り返しがつかない。仕様書まで書いて止め、user に渡す
3. **既存の挙動が変わる**（しきい値・既定値・順番・文言の変更、機能の削除）
   … 一言のアイデアから勝手に決めてよい範囲を越えている
4. **仕様が書けない**… 読み方が2通りあって、どちらかで作るものが変わるなら、
   工程2で「未決」を並べて止まる。**推測で埋めて先へ進まない**
5. **同じ場所を3周しても テストが通らない**（工程4）… 何を試して何が
   起きたかを書いて止まる
6. **`npm run verify` が落ちた**… 落ちたままコミットしない

止まったときは、**そこまでの成果物（ブランチと仕様書）は残す。** 捨てない。

## 勝手に決めたことを、必ず表に出す

止まるほどではない小さな判断（名前・並び順・既定値・どこへ置くか）は、
**決めて進んでよい。ただし記録する。**

- 仕様書に **「## 決めたこと（確認してほしい）」** の節を作り、
  判断と根拠を並べる
- **PR 本文の冒頭にも同じ内容を載せる。** PR がこのパイプラインの
  唯一のレビュー地点になる
- 「なんとなく」で決めたものは、そう書く。**それらしい理由を作らない**

## 各工程の実務

**1** — `main` から切る。`origin/main` が進んでいたら先に追いつく。
`maintenance/` は保守点検ルーティンの予約なので使わない。

**2** — 読むのは関係する所だけ（`docs/architecture/overview.md` /
`docs/data-model.md` / `docs/features/README.md` / 該当する `.claude/rules/`）。
**数字を書かず定数名を書く**（`docs/README.md`「数字を写さない」）。

**3** — `npm run test` は **watch モードで終わらない**。必ず
`npx vitest run <パス>`。データは `src/test/factories.ts` の `make*`。
**書いたテストが本当に落ちることを確かめてから 4 へ行く。**

**4** — テストを通すために**テストの方を緩めない**（期待値の書き換え・
`skip`・握り潰し・型を緩める）。純粋な計算は `features/<domain>/lib/` へ。

**5** — 対象は「機能を足した / 挙動を変えた / 機能を消した / バグを直した」。
内部の整理だけなら回さない。手順は `.claude/skills/qa-checklist/SKILL.md`。
**Artifact は必ず同じ URL へ再公開する**（別の台本を作らない）。

**6** — `git add .` の前に `git status --porcelain` で未追跡ファイルを一覧し、
**見覚えの無いものは中身を見る**（落とし物が混ざる）。
コミット前に `npm run verify`。

**7** — `main` に居たら作らない（1 が成功していれば起きない）。
本文は差分の要約ではなく**選ばなかった案と理由**。
**確認していないことを確認したと書かない**（実機未確認ならそう書く）。
**マージはしない。**

**8** — 書くのは「起きたこと」ではなく**「次はどうするか」**。
**学びが無ければ書かない。** 無理に1件ひねり出すと、次から読まれなくなる。

## いつ使うか

**小さくて、輪郭がはっきりしている追加**に向く
（「シーンを複製したときに名前へ (2) を付ける」くらいの粒度）。

**向かないもの**: 既存の挙動を変える / 画面の作りを変える / データの持ち方を
変える / 「なんとなくこうしたい」。これらは `/spec` で仕様を詰めてから、
工程を分けて進めた方が速い。**一気通貫は、間違えたときの手戻りが最大**。
