---
description: 変更差分を分析し、規約に従ったコミットメッセージを生成して自動コミットする
---

現在の作業ツリーの変更内容に対して、以下のステップを自律的に実行してください（すべて許可不要）。

1. `git status` および `git diff`（必要に応じて `git diff --staged`）を実行し、変更内容を詳細に分析する。
2. Conventional Commits の規約に従い、適切なプレフィックス（`feat:`, `fix:`, `refactor:` など）を用いた英語（または日本語）のコミットメッセージを生成する。メッセージは「何を変更したか」だけでなく「なぜ変更したか」も含めること。
3. `git add .` を実行して全ての変更をステージングする。
4. 生成したメッセージを用いて `git commit -m "メッセージ"` を実行する。
5. 「以下の内容でコミットを完了しました」として、実行したコミットメッセージを出力する。

---

## 2 について（このリポジトリの形に合わせる）

**このリポジトリは Conventional Commits を使っていない。** 全履歴が
「日本語・プレフィックス無し・何をしたかを一文で」で揃っている。

```
マウスで囲んで選ぶ。払って送るは指のものにする
リファクタリング（挙動は変えない。測って見つけた3箇所）
狭めたら端へ寄せる。入れられない数は押す前に止める
```

**ここに `feat:` を混ぜると履歴が2種類になる。** changelog もリリース自動化も
無いので、プレフィックスから得られるものが無い。指示にも
「英語（または日本語）」とあるので、**日本語・プレフィックス無しで揃える**。
（変えたければ言ってください。その場合は過去の分は揃わない、という前提で。）

書き方:

- **1行目は「何をしたか」を一文。** 型やファイル名ではなく、**変わったこと**を書く
- **本文に「なぜ」を書く。** 何を試して駄目だったか、何を選ばなかったかも
- **1コミット = 1つの目的。** リファクタリングと挙動の変更を混ぜない
  （混ぜると、壊れたときにどちらが原因か分からなくなる）
- 複数行なので `-m` ではなくヒアドキュメントを使う:

```bash
git commit -F - <<'MSG'
一行目

本文（なぜ変えたか）

Co-Authored-By: Claude Opus 5 (1M context) <noreply@anthropic.com>
Claude-Session: <このセッションの URL>
MSG
```

**trailer は例の中に入れてある。** 前は「末尾に付ける」と注意書きだけ
置いていたが、**例を写して trailer が落ちた**（2026-08-18 に実際にやった）。
手順に例があるなら、読まれるのは例の方。注意書きではなく例を正しくしておく。

## 3 の前に、必ずやること

**`git add .` をそのまま実行しない。** 過去に、作業中へ置いた参照用の画像が
そのままコミット・push された。`.gitignore` に後追いで守りを足してあるが、
**新しい種類の落とし物は素通りする。**

```bash
git status --porcelain              # 追跡されていないファイル(??)を必ず一覧する
```

- **見覚えの無いファイルがあれば、開いて確かめてから足す。** 画像・書き出し・
  ログ・鍵が混ざっていないか
- 心当たりが無いものは**足さずに user へ言う**
- 確かめた結果、関係ないものが混ざっているなら **`git add .` ではなく
  パスを名指しして足す**

### `add` を絞っても、`commit` は索引ぜんぶを取る

**これが本命の落とし穴。** `git add <パス>` で自分の分だけ足しても、
`git commit` は**索引にある全部**をコミットする。user が先にステージして
あった作業を巻き込んだことがある（2026-08-18・timelag で 1037 行）。

```bash
git status --short                  # ← 索引(左の桁)に自分以外が居ないか見る
git commit -F - -- <パス> [<パス>]  # ← 迷ったらパスを名指しする形で出す
```

**`--` の後ろを書けば、索引に何が入っていても指したものだけが入る。**
巻き込んだら `git reset --soft HEAD~1` で戻し、名指しの形で取り直す
（相手のステージはそのまま残る）。

## 4 の前に、必ずやること

**`src/` に変更があるなら、先に通す。**

```bash
npm run verify        # lint → test → build
```

コミットフックは `eslint --fix` しか走らせない（`lint-staged`）。
**テストとビルドは誰も見ていない**ので、ここで通す。落ちたままコミットしない。

**画面に見える変更を含むなら、コミットの前に `/qa-checklist` を回す。**
機能を足した / 挙動を変えた / 機能を消した / バグを直した、が対象。
内部の整理・型・テストだけなら回さない。
（これは `CLAUDE.md` の決まりで、飛ばしてよいのは user が明示したときだけ。）

## push（2026-08-18 に事前承認をもらった）

**このリポジトリは、verify が通っていれば訊かずに push してよい。**
user は Vercel の本番で動作確認するので、**push していない変更は
user から見えない**。手元に留める方が邪魔になる。

- **verify が落ちていたら push しない。** 赤いまま本番へ出さない
- push したら、**画面に見える変化があるかどうか**まで1行で伝える
- **他のリポジトリへ持ち込まない。** これは「デプロイ先で確認する」という
  流れに付いた承認で、手元で確認するプロジェクトには当てはまらない

これでも一言置くもの: スキーマ変更 / ファイル・データの削除 /
force-push / 外部サービスへの送信。
