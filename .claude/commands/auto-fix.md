以下のステップを、**人間に許可を求めず**連続して自律的に実行してください。

1. 報告されたバグや、直近のターミナルエラーログを分析する。
2. 必要に応じて関連ファイルを読み込み、原因を特定する。
3. `any` 型を一切使用せず、厳格な TypeScript の型定義と例外処理を用いて修正コードを実装する。
4. 修正後、静的解析やビルドを自動実行し、エラーが完全に解消されたか確認する。
5. エラーが残っていればステップ2に戻り自己修正する。解消していれば、今回の原因と対策を `docs/lessons_learned.md` に追記して完了報告を行う。

---

## このリポジトリでの具体

**4 で流すもの**（速い順。落ちた所で止めて直す）:

```bash
npx tsc --noEmit                  # 型だけ見たいとき
npx vitest run <絞ったパス>       # 関係するテストだけ
npm run verify                    # 最後に通し（lint → test → build）
```

**直す前に、その挙動を確かめるテストがあるか見る。** 無ければ足してから直す。
直したら**直した側を一時的に戻して、テストが本当に落ちることを確かめる**。
落ちなければ、そのテストは何も守っていない。

`any` を使わずに逃げ道が要るときは `unknown` + 絞り込み。
Supabase のエラーは `src/lib/supabase/errors.ts` の `toUserMessage` を通す
（user に出す文言はそこに集めてある）。

## 止まる条件

**同じ場所を3周しても直らなければ、そこで止めて報告する。**
直し方が分からないまま4周目に入ると、関係の無い所まで書き換えて傷が広がる。
報告するのは「何を試して、何が起きたか」「いま何が分かっていないか」の2つ。

**原因が分からないまま、症状だけを消さない**（`try {} catch {}` で握り潰す、
型を緩める、テストを消す）。それは直したことにならない。

## 画面に見える変更を含んだら

コミットの前に `/qa-checklist` を回して、再発を捕まえる項目を足す。
