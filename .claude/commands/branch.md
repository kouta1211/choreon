---
description: 作業内容の概要から、適切なプレフィックスを持つGitブランチを自動作成してチェックアウトする
---

ユーザーから「ログイン機能の追加」「ボタンのバグ修正」などの作業概要を受け取り、以下のステップを自律的に実行してください。

1. 作業内容を分析し、適切なプレフィックス（`feat/`, `fix/`, `refactor/`, `docs/` など）を選択する。
2. 作業内容を英語のケバブケース（ハイフン繋ぎ）に翻訳し、ブランチ名を生成する（例: `feat/add-login-function`）。
3. `git checkout -b <生成したブランチ名>` を実行し、新しいブランチに移動する（許可不要）。
4. 「ブランチ '<ブランチ名>' を作成し、移動しました。作業を始めてください。」と報告する。

---

## 3 の前に、必ず見ること

**切る前の状態を確かめる。ここを飛ばすと、古い土台の上で作業が始まる。**

```bash
git status --short          # 汚れていないか
git branch --show-current   # いまどこに居るか
git fetch origin && git log --oneline -1 origin/main   # main は進んでいないか
```

- **作業ツリーが汚れていたら、切る前に user へ言う。** 未コミットの変更は
  新しいブランチへ付いてくる。それが意図したものとは限らない
- **main 以外に居たら、そこから切ってよいか確かめる。** 黙って枝の枝を作らない
- **`origin/main` が進んでいたら、先に追いつく**
  （`git switch main && git pull` してから切る）

## 名前の付け方（このリポジトリの実態）

既存のブランチは `scene-scrub-morph` `dancer-touch-feedback` `music-sync` の
ように**プレフィックス無しのケバブケース**。指示の `feat/` `fix/` 形式は
ここから変わるが、ブランチ名は残らないので**そのまま従ってよい**。

**`maintenance/` は使わない。** 3日に1回の保守点検ルーティンが
`maintenance/YYYY-MM-DD` で使っている（`.claude/skills/daily-maintenance/`）。
手作業のブランチと混ざると、どちらの成果物か分からなくなる。

接頭辞は指示の4つ（`feat/` `fix/` `refactor/` `docs/`）に加えて、
**`test/`**（テストだけを足す）と **`chore/`**（設定・依存・雑務）も使う。
最初の試運転で `test/` が要ることが分かった。

短くする。`feat/add-login-function` で十分で、
`feat/add-login-function-with-supabase-auth-and-error-handling` にしない。

## 知っておくこと（今の運用）

**このリポジトリは、いま main へ直接コミットしている**（履歴を見れば分かる）。
ブランチを切ると、そのままでは本番へ出ない。**PR を出してマージするまでが
一続き**になる。CI は `main` への push と、`main` 向けの PR で走る
（`.github/workflows/ci.yml`）。

だから `/branch` を使うのは、**分ける理由があるとき**にする:

- 途中で main を触りたくなる（別の急ぎが入りそう）
- 実験で、捨てるかもしれない
- レビューを挟みたい

そうでなければ、main のまま進めた方が速い。**手段が目的にならないように。**
