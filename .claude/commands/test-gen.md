---
description: 仕様書や要件から、実装前に「振る舞いを定義する厳格なテストコード」を自動生成する
---

ユーザーが指定した機能要件や仕様書（`docs/features/` 等）を読み込み、以下のステップを自律的に実行してください。

1. 仕様を満たすためのテストケース（正常系・異常系・エッジケース）を洗い出す。
2. 実際のコンポーネントやロジックを実装する「前」に、Vitest を用いたテストファイル（例: `xxx.test.tsx`）を自動生成する。
3. テストコード自体も `any` を排除し、プロジェクトの型定義に厳密に従うこと。
4. ファイル保存後、「テストコードを生成しました。現在は実装がないためテストは失敗します。`/test-pass` で実装を開始してください」と報告する。

---

## 指示から変えたこと

- **仕様書は `docs/features/`**（`docs/02_features/` は存在しない）。
  地図は [docs/features/README.md](../../docs/features/README.md)
- **Jest は入っていない。Vitest だけ。**（`jest` は `choreon-app/` の
  ネイティブ版が使っているが、あれは停止中の別プロジェクトで、
  ルートの vitest は `choreon-app/**` を除外している）

## 置き場所と書き方

**テストは対象の隣に置く。** `marquee.ts` の隣に `marquee.test.ts`、
`SceneList.tsx` の隣に `SceneList.test.tsx`。別のディレクトリへ集めない。

```ts
import { describe, expect, it } from "vitest";
import { makeProject, makeScene, makeDancer, makePosition } from "@/test/factories";
```

- **データは `src/test/factories.ts` の `make*` を使う。** 自前でオブジェクトを
  組み立てない（型が変わったとき、ここだけ直せば全部追随する）
- **`it()` の説明は日本語で、振る舞いを書く。** 「客席を上にしているときは、
  画面の向きで選ぶ」のように、**読めば仕様が分かる**文にする。
  `should return true` のような関数名の言い換えにしない
- `@` は `src/` のエイリアス（`vitest.config.ts`）。相対パスで遡らない

## 洗い出しの観点（このアプリで実際に壊れた所）

- **境目**: 0 / 最大値 / 空の配列 / 1件だけ
- **向きの反転**: 「客席を上にする」がオンのとき（`stageFlip`）。
  **オフだけ書いて通ったテストは、半分しか見ていない**
- **はみ出し**: ステージの外へ出る値。まとめて動かすときは
  **形が保たれるか**（1人だけ端で止まって隊形が潰れないか）
- **入力機器**: マウスと指で意味が変わる操作がある
  （[ADR 0001](../../docs/architecture/decisions/0001-pointer-type-split.md)）
- **失敗したとき**: 保存が失敗したら**画面が元へ戻る**か、
  **履歴に積まれない**か
- **同じ値**: 変わっていない値を保存しようとしていないか

コンポーネントのテストは「押したら何が起きるか」だけを見る。
内部の状態を覗きに行かない。

## 4 の報告の前に

**本当に失敗することを確かめてから報告する。**

```bash
npx vitest run <生成したファイル>
```

「実装が無いから落ちるはず」と書いて出さない。
**通ってしまったら、そのテストは何も定義していない。**
