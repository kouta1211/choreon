---
description: 修正やリファクタリングの前に、依存関係と影響範囲を徹底的に調査する
---

ユーザーが指定したファイルやコンポーネントについて、コードを書き換える前に以下の調査を自律的に実行し、レポートを出力してください。

1. **依存関係のマッピング:** そのファイルが「どこから呼び出されているか」「何を呼び出しているか」を検索（grepなど）を用いて特定する。
2. **状態と型の分析:** 影響を受ける Props や State、Supabase の型定義を洗い出す。
3. **リスク評価:** このコードを分割・修正した場合に壊れる可能性のある機能をリストアップし、安全に改修するための手順を提案する。

---

## 1 の探し方（このリポジトリでの注意）

**`git grep` を使う。** 素の `grep -r` は `node_modules` と `.next` まで舐めて
時間を溶かす。

```bash
git grep -n "<名前>" -- src            # 呼び出し元
git grep -n "^import\|from \"@/" -- <ファイル>   # 呼び出し先
```

**`-- src` を必ず付ける。** `src/`（Next.js・本体）と `choreon-app/`
（Expo・停止中）に**同名のファイルが多数ある**（`useUIStore.ts`
`useProjectStore.ts` `sceneTiming.ts` など）。付けないと、止まっている方の
参照まで数えて影響範囲を見誤る。

**動的な参照も探す。** import だけ追うと漏れる:

- `data-testid` … テストとスキルが名指ししている
- i18n のキー … `git grep -n "<キー>" -- src/features/i18n`
- 文字列で引いている CSS 変数・テーマ名

## 2 で見るもの

| 種類 | 置き場所 |
| --- | --- |
| DB の型 | `src/lib/supabase/database.types.ts`（**生成物**。手で直さない） |
| ドメインの型 | `src/features/<domain>/types.ts` |
| 状態 | `useProjectStore`（作品）/ `useUIStore`（画面）/ `useHistoryStore` ほか。役割は [.claude/rules/state.md](../rules/state.md) |

**props とストアのどちらから来た値かを必ず分ける。** サーバーが渡した props は
編集しても古いままで、描く側は `EditorLayout` の `live` 経由でストアを優先して
読んでいる。ここを取り違えると「数字は変わるのに画面が変わらない」を作り込む。

## 3 のリスク評価に必ず入れるもの

- **テストがあるか。** 隣に `<名前>.test.ts(x)` があるか。
  **無ければそれが最大のリスク**で、直す前にまずテストを足す
- **画面に出るか。** 出るなら `docs/qa-checklist.html` の該当章
  （`grep -n` で探す。**188KB あるので全部開かない**）
- **保存に関わるか。** 【楽観的に変える → 保存 → 失敗したら戻す】の
  どこに居るか。履歴（元に戻す）に積まれる操作か
- **端末で挙動が変わるか。** マウスと指で意味を変えている操作がある
  （[ADR 0001](../../docs/architecture/decisions/0001-pointer-type-split.md)）。
  `pointerType` や `screenKind` を見ているコードは、両方で確かめる
- **3言語そろっているか。** 文言を動かすなら ja / en / ko

## レポートの形

```
## 呼び出し元（N件）
- path:line — どう使っているか

## 呼び出し先
- 純粋な計算 / ストア / Supabase / 外部ライブラリ に分けて

## 型と状態
- どの型が跨っているか。props とストアのどちらから来ているか

## 壊れうるもの（危ない順）
1. <機能> — 理由 / テストの有無 / 台本の該当章

## 安全に進める手順
1. …（**テストを足す → 割る → 通す** の順で書く）
```

**分からなかったことは「分からなかった」と書く。** 埋めない。
