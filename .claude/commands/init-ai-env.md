description: いまのリポジトリを分析して、AI が迷わず開発できるコンテキスト環境（rules / docs / CLAUDE.md / 除外設定）を構築する
argument-hint: [プロジェクトの一言説明（省略可）]
---

このリポジトリに**AI 用のコンテキスト環境**を作る。

**汎用テンプレートを貼らない。** 中身を読んで、このリポジトリ固有の
「AI が迷う所」を潰す形で組む。テンプレートを当てただけの docs は、
2週間で全部古くなって誰も読まなくなる。

$ARGUMENTS があれば、それをプロジェクトの説明として使う。

---

## Step 1. 現状を読む

**書き始める前に、必ず全部やる。** ここを飛ばすと汎用テンプレートになる。

```bash
ls -la
git ls-files | awk -F/ 'NF>1{print $1}' | sort | uniq -c | sort -rn   # 上位ディレクトリの規模
```

見るもの:

1. **技術スタック** … `package.json`（または `pyproject.toml` / `go.mod` /
   `Cargo.toml` / `*.csproj`）の依存と scripts。**バージョンまで見る**
   （メジャーが上がっていると、AI の記憶と作法がずれる）
2. **関心事の分け方** … ソース配下を2階層まで数え、**どういう規則で
   分かれているか**を言葉にする（層で分けている / ドメインで分けている /
   その両方が直交している、など）
3. **既にある説明** … `README*` `AGENTS.md` `CONTRIBUTING*` `docs/**`、
   および**ソースの中の README**（`src/**/README.md`）。
   ユーザーのグローバル `~/.claude/CLAUDE.md` も読む
4. **決まりごとの機械的な担保** … lint 設定・CI（`.github/workflows/`）・
   husky / lint-staged・テストの置き方
5. **データの持ち方** … スキーマ・マイグレーション・型の生成物

### そして「AI が迷う所」を名指しする

ここが本体。**最低3つ挙げるまで次へ進まない。** よくあるもの:

- **同名のファイルが2箇所にある**（モノレポ、旧版が残っている、
  Web 版とネイティブ版が同居）→ 検索が二重に当たり、違う方を直す
- **巨大なファイル**（生成物・1枚 HTML・ロックファイル）→ 開くと context が飛ぶ
- **規約が散っている**（README・コード内 README・グローバル設定）→ 入口が無い
- **記憶と違うバージョン**が入っている → 記憶で書いて壊す
- **生成物なのに手で直せてしまう**ファイル

ここまでを**表にして user へ見せてから**、Step 2 へ進む。

## Step 2. 環境を作る

**既存のファイルを壊さない。** 上書きではなく、足す・整えるだけ。

### `.claude/rules/`

**分析した技術スタックに合わせて分ける。** 決め打ちの
`frontend.md` / `backend.md` にしない。目安:

- フロントとサーバーが分かれている Web → `frontend.md` `backend.md`
- 状態管理が重い → `state.md` を独立させる
- ゲーム → `gameplay.md`（ループ・入力・当たり）`assets.md`（命名・容量）
  `performance.md`（フレーム予算）
- CLI / ライブラリ → `api-surface.md`（公開 API の壊し方）`errors.md`
- テストの決まりは、どのスタックでも独立させる価値がある → `testing.md`

必ず `.claude/rules/README.md`（索引）を置き、**Step 1 で名指しした
「最初に踏む地雷」をそこへ書く**。

書くのは「このリポジトリで間違えること」だけ。一般論
（「変数名は分かりやすく」）を書かない。**数字・ファイル名・実際に
壊れた例**を入れる。

### `docs/`

```
docs/
├── README.md                     どこに何を書くかの表
├── architecture/
│   ├── overview.md               全体の構造・データの流れ
│   └── decisions/                ADR。README.md と _template.md
├── data-model.md                 （データを持つプロジェクトなら）
├── features/
│   ├── README.md                 機能の地図（1機能1行）
│   ├── _template.md
│   └── <実物を1つだけ>.md        書き方の見本
└── lessons_learned.md            失敗の記録
```

**全部の機能ドキュメントを先回りして書かない。** 触った分だけ増やす形にする。
先に揃えると、触っていないファイルから先に嘘になる。

**しきい値・既定値・秒数を docs に書かない。** 定数の**名前と置き場所**を書く。
数字を写すと、コードを直したときに docs が黙って嘘になり、しかも誰も気付かない。
（例外は、人が画面を見て○×を付ける確認用の台本だけ）

**`decisions/` と `features/` には、実物を1つずつ置いてから渡す。**
雛形だけのディレクトリは「使い方が分からない箱」になって、そのまま空で残る。
今回の作業中に決めたこと（除外の置き場所など）が、そのまま最初の ADR になる。

`features/README.md` の地図（1機能1行）は**必ず作る**。これがあるだけで、
AI が「どこを見ればいいか」で迷わなくなる。

既に README に決定の経緯が書いてあるなら、**ADR へ写さない**。
`decisions/README.md` に「過去は README が正、これからはここ」と書く。

### `.claudeignore`

**先に、いまの CLI が本当に読むのかを確かめる。**

```bash
CLI=$(command -v claude); grep -c "claudeignore" "$CLI" || true
```

（`grep -c` は**一致0件のとき exit 1 を返す**。`|| true` を付けないと、
`set -e` の下や連結したコマンドの途中で処理が止まる。）

0 だったら **`.claudeignore` は効かない**。実効性は
`.claude/settings.json` の `permissions.deny` に持たせる。

**一覧は片方にだけ書く。** `.claudeignore` にも同じ一覧を書き写したくなるが、
**2つの一覧は必ずずれる**。片方だけ直したときに、効いていない方を信じて事故る。
`.claudeignore` は残すなら**案内文だけ**にして、調べた結果は ADR に書く
（「なぜ2つあるのか」を次に調べ直させない）。

弾くもの: 秘密情報 / ビルド成果物 / ロックファイル / 巨大な生成物 / バイナリ。

**弾いてはいけないもの**を先に確認する。よくある事故:

- `node_modules/` を丸ごと弾く → 「ライブラリの実物を読んで確かめる」
  という規約が守れなくなる
- スキル・コマンドが編集するファイルを弾く → そのスキルが動かなくなる
  （巨大でも塞がず、「全部読まず grep で当たりを付ける」と書く方を選ぶ）

### `.claude/commands/`

無ければ作る。**既にあるものを消さない。**

## Step 3. `CLAUDE.md`

既にあれば**中身を残したまま**、先頭に次の2つを足す。

1. **AI 用コンテキストの目次** … Step 2 で作ったファイルへの表。
   「いま触る所の分だけ開く」と明記する（全部読ませない）
2. **このプロジェクト固有の振る舞い**
   - Step 1 で名指しした地雷への注意
   - **いま機械で守られていること**の表（lint ルール名・型の設定・
     verify の並び）。ここが下がったら直す、と書く
   - 記録の置き場所（`docs/lessons_learned.md` / 昇格先の `.claude/rules/`）

**どこに書くかを間違えない。**

- **全プロジェクトに共通する振る舞い**（説明の量、自律の範囲、品質の原則、
  学びの記録の作法）は**グローバルの `~/.claude/CLAUDE.md` が正**。
  プロジェクト側へ写さない。**2箇所に置くと必ずずれる**
- プロジェクトの `CLAUDE.md` に置くのは、**そのリポジトリでしか成り立たない
  こと**だけ

グローバルと矛盾する必要が出たら、**勝手に狭めず user に確かめる**。
どちらが優先かを本文に書き、日付を添える
（例:「軽微な修正についてはこちらを優先する（YYYY-MM-DD 決定）」）。

## Step 4. 確かめて渡す

```bash
node -e "JSON.parse(require('fs').readFileSync('.claude/settings.json','utf8'))"  # 設定が壊れていないか
git status --short                                                                # 何を足したか
```

- 作ったファイルの**リンクが全部つながっているか**（相対パスの深さを間違えやすい）。
  この確認は**繰り返し回る仕組みに埋める**。docs は黙って腐るので、
  定期の点検ルーティンや CI があるなら、そこにリンク切れの検査を1本足しておく
- **既存のファイルが消えていないか**
- user へは「何を作ったか」ではなく**「次に何が変わるか」**を伝える

## やらないこと

- ソースコードを直す（ここは環境を作る作業）
- 中身の薄いドキュメントで数を揃える。**1枚も書かない方がまし**
- コードの隣に既にある説明を docs へ写す（必ず片方が古くなる）
- 分析を飛ばしてテンプレートを貼る
