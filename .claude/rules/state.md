# 状態の持ち方（Zustand）

## 1. ストアは役割で分かれている。混ぜない

| ストア | 何を持つか |
| --- | --- |
| `features/project/store/useProjectStore` | **作品そのもの**。タイトル・ステージ・ダンサー・立ち位置 |
| `features/canvas/store/useUIStore` | **画面の状態**。選択中・トースト・開いているシート |
| `features/canvas/store/useHistoryStore` | 元に戻す / やり直す |
| `features/settings/store/useSettingsStore` | 端末に残す設定（作品ではなく人の好み） |
| `features/music/store/useMusicStore` | 曲と再生位置 |
| `features/viewer/store/useViewerStore` | 閲覧画面だけの状態 |
| `features/theme/store/useThemeStore` | テーマ |

**分けている理由**: 作品は Supabase へ保存するもの、画面の状態は保存しないもの。
選択中のダンサーを `useProjectStore` に入れると、保存の差分に混ざる。

## 2. サーバーから来た props と、ストアの中身がずれる

`/projects/[id]` はサーバーで作品を読んで props で渡す。**編集するとストアだけが
新しくなり、props は古いまま**。props を素直に描くと「数字は変わるのに画面が
変わらない」という壊れ方をする（実際に起きた: 報告 03-17）。

編集で変わりうるものを描く側は、**ストアを優先して読む**:

```ts
const live = useProjectStore((state) =>
  state.project?.id === project.id ? state.project : project,
);
```

`src/components/templates/EditorLayout.tsx` がこれを1箇所でやって、
下の組へは `live` を配っている。**新しく props を足すときは、そこへ足す。**

## 3. 保存の型は決まっている

**楽観的に画面を変える → 保存する → 失敗したら戻す → 成功してから履歴に積む。**
立ち位置の編集は `features/scene/hooks/usePositionCommit` に1本化してあるので、
新しい編集操作もここを通す（`changes[]` と `kind` を渡すだけ）。

- **失敗した操作を履歴に積まない。** 見た目は戻っているので、積むと
  「元に戻す」の辻褄が合わなくなる
- 矢印キーの連打は `hasSameTargets` が同じ対象の連続を見て**1ステップに畳む**。
  だから `changes[]` の並びは操作ごとに安定させる

## 4. 同じ tick で2回コミットするときは `getState()` を読む

レンダー時のクロージャに閉じ込めた値は古い。まとめて適用するボタンのように、
1回の処理で複数の変更を流すときは `useProjectStore.getState()` で**その場の最新**を
読む。読まないと、後の1つが前の1つを巻き戻す（設定の一括適用で実際に起きた）。

## 5. 選択は「並び」で持つ

`useUIStore.selectedDancerIds: string[]`（複数選択があるため）。
1人のときだけ出したいもの（インスペクター・回転ハンドル・曲線）は、
自前で長さを数えず `selectPrimaryDancerId(state)` を読む。

## 6. 値の見せ方を変えたら、その値に触る所を全部数え直す

**2026-08-19 に1日で2回踏んだので、ここへ上げた。**

シーンの時刻を「順番だけ」に変えたとき、

1. その値を**書き換える操作**（追加・並び替え・削除）が、user の決めた
   秒数を黙って半分にしていた
2. その値を**表示する場所**（下のバーの時計・一覧の見出し・ダンサーの詳細）に
   秒数が残っていて、「消えていない」という報告が来た

どちらも「表示だけの変更」のつもりだった。**user が読む数が変われば、
正しさの基準もそこで変わる。**

新しい見せ方を入れるときは、書く前に2つ数える。

```bash
git grep -n "<その値の名前>" -- src | grep -v test    # 触る所
```

- **書き換える側** … その操作の後で、新しい見せ方と辻褄が合うか
- **見せる側** … 出しては困る数字が残っていないか
- **説明する側** … その値のことを書いた文（使い方の案内・動作確認の台本・
  コードのコメント）が、新しい見せ方と食い違っていないか

どれかの一覧が3つを超えたら、**判断を1箇所に閉じ込めてから**手を付ける
（`useSceneSummary` と `features/scene/lib/outgoingSegment.ts` がその形）。
各画面で条件を書くと、必ずどこかが取り残される。

⚠️ **閉じ込めても、生で書かれた1箇所は型に出ない**（2026-08-26）。
「順番だけか」の判定を hook に閉じ込めていたが、`useAddScene` だけが
同じ条件を**その場で書いて**いた。hook を消しても型エラーが出ず、
**シーンを足したときだけ全部が積み直される**状態が残った。
閉じ込めた条件を畳むときは、`git grep` で**名前だけでなく、
その条件式そのもの**も探す（`!hasMusic && !isMetronomeEnabled` の形）。

**「見せる側」には、見る側の画面（`/view`）も入る**（2026-08-21）。
2026-08-19 に時刻を隠したとき、作る側の3箇所は数えたのに**閲覧画面の5箇所が
まるごと漏れていた**。作る側と見る側は同じ値を別の道で描いていて、
`git grep` の相手も別（`useViewerStore`）。**片方だけ数えて終わりにしない。**

⚠️ **依存しているのが「値」ではなく【いつ起きるか】のこともある**
（2026-08-31）。再生の模型を「シーンへ入ってくる区間」から
「次へ出ていく区間」へ変えたら、**2件の不具合が連鎖した**。

- 導線の跡は「**シーンが変わったとき**」に出す作りだった。古い模型では
  それが移動の始まりと同じ瞬間だったので、成立していただけ
- 名前の層は位置を CSS で直に置いていた。**丸が滑らかに動くようになって
  初めて**、名前だけ行き先へ飛ぶことが見えた

どちらも `git grep` で名前を追っても出てこない。**その値を読んでいないから。**
読んでいるのは「その値が変わる**タイミング**」の方で、grep の相手が無い。

→ **タイミングを変えたときは、そのタイミングに合わせて動いていたものを
数える。** 探し方は名前ではなく、**「いつ」で書かれている所**:

```bash
# 「変わったら作り直す」「前回と違ったら始める」で書かれた所。
git grep -nE "key=\{[a-zA-Z]+(Scene|Dancer)Id\}|useState\((selectedSceneId|isPlaying)\)" -- src | grep -v test
```

⚠️ **広く採らない。** 上は通して **4件**（2026-08-31 時点）で、今日の2件は
どちらもこの中に居た。`previous` や `!== ...Id` まで拾う書き方だと **112件**
出て道具にならない（実際に書いてから通して捨てた）。

同じ模型に**式を写して**ぶら下がっている所も数える。同じ動きをさせたい
2つは、式を写さず**動かし手（フック）ごと共有する** — 写した側は、
元が変わった日に静かに嘘になる（`useDancerMotion` を名前の層にも通した）。

**「説明する側」は、画面が動くので気づけない**（同日）。使い方の案内が
「コマは曲の何秒目か」と言い続けていて、**初めて開く人には必ず食い違って
いた**（その人の作品に曲は入っていない）。台本にも、存在しない画面を
「出る」と書いた項目が残っていた。**説明を機械で縛れる形に置く**のが答えで、
案内は `features/tutorial/lib/tourSteps.ts` の純粋関数へ出してテストで
固定してある。

## 7. 同じ問いに答える口を、2つ置かない

**2026-08-26 に1日で3回踏んだので、ここへ上げた。**

どれも「同じことを言う値が2つあって、**測っている物差しが違う**」形。
片方を直しても、もう片方は嘘のまま残る。

| 何が2つあったか | どうずれたか |
| --- | --- |
| 拍の原点と、曲の再生開始位置 | 軸が違う（作品の時間 / 曲の時間）ので**二重に足していた** |
| 「振付が曲の何秒目から始まるか」を言う列が2つ | `music_offset_seconds` と placement の `atSeconds` |
| 速さのスライダーが2箇所（時間軸の下・曲のシート） | 意味を直すとき、片方を見落とせば静かにずれる |

**畳めるなら畳む。畳めないなら、どちらが正かを型か構造で言い切る**
（コメントに書いても読まれない）。`BeatOriginSeconds` は後者の形で、
**素の `number` を受け付けない**ので取り違えるとコンパイルが落ちる。

### 単位を名前に持たせない

**同じ日に2回出た。** `splitSegment` と `segmentBar` は
「区間から移動を引く」だけの計算で、**秒でも拍でも同じ式**。
`holdSeconds` / `stepSeconds` という名前のまま拍を入れたので、
**正しく動くのに名前だけが嘘**になった。

- 単位に依らない計算 … `hold` / `move` / `segment` / `step`
- 単位が決まっている値 … 名前に付ける（`positionBeats` / `timeSeconds`）

**刻みを引数で受ける部品は、単位ごとに分ける。** `stepSeconds` に
既定値（0.1）を置いていたので、カウント用に流用したとき
**渡し忘れた呼び出しだけが 0.1 刻み**になりうる（型は通る）。
`CountLengthInput` と `DurationSecondsInput` は、そのために別の部品。

### 機能を1つ畳んだら、その機能のためだけにあった道具を数える

**同じ日に2回出た**（`snapSeconds`、頭出しの試し聴きの hook）。
**lint は未使用の export を見ない**ので黙っている。
文言だけは `check:docs` が拾う。

```bash
# 定義とテストしか出てこない名前が、余った道具
git grep -n "<名前>" -- src | grep -v test
```

残すと「曲があるときだけ細かく置けた方が」と手が伸びる。
**畳む前に一覧を作る**のが早い（畳んだ後に探すと、必ず1つ残る）。
