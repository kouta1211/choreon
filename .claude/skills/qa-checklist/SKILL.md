# 動作確認チェックリストの更新

user は実装を**自分の手と目で**確かめる。その台本がこのファイル。
**実装した本人（＝あなた）しか、どこを触れば新しい挙動が出るかを知らない。**
ここを更新し忘れると、その機能は誰にも確認されないまま出荷される。

## 0. いつ回すか

コードを変えて `npm run verify` が通ったら、**コミットの前に**回す。
以下のどれかに当てはまれば必ず更新が要る。

- 画面に見える機能を足した
- 既存の挙動を変えた（しきい値・既定値・順番・文言）
- 機能を消した → **古い項目を消す。これを忘れるのが一番たちが悪い**
  （user が「動かない」と報告してくるが、実際には仕様どおり消えている）
- 直したバグ → 再発を捕まえる項目を足す

UI に現れない変更（内部の整理・型・テストだけ）なら**更新しない**。
項目が増えるほど一巡が重くなり、通しで確認されなくなる。

## 1. 触るファイル

`docs/qa-checklist.html` の1枚だけ。中の `<script>` にデータがある。

| 置き場所 | 何が入るか |
|---|---|
| `SHARED(isPhone)` の戻り値 | **両方の端末で確かめる項目**。ほとんどはここ |
| `DATA.phone.acts` の末尾側 | 実機（タッチ・実際の画面の高さ・PWA・電波）でしか出ないもの |
| `DATA.pc.acts` の末尾側 | キーボード・マウスのホバー・窓幅の切り替えでしか出ないもの |

`SHARED` は関数で、`isPhone` から `tap`（触る/押す）・`drag`・`finger` を作っている。
両方に出す文はこれを使い、端末ごとに言い回しを変える。

## 2. 項目の書き方

```js
{
  n: true,                                  // 今日実装したぶんなら付ける（「今日の分」で絞れる）
  do: "設定 → 舞台 → <em>客席を上にする</em> をオン",
  ok: "上の札が「客席側」、下が「バックステージ」に入れ替わる。同時に全員が上下にひっくり返る",
  ng: "左右も動いてしまったら不具合です",   // 任意
}
```

守ること。**ここが崩れると、前回のように「わかりにくくて確認できなかった」に戻る。**

- **`do` は場所から書く。** 「設定 → 舞台 → 客席を上にする」のように、
  ホームなのかエディタなのか、どのシートの何段目なのかまで辿れること。
  実際に押すものを `<em>` で囲む（画面上で色が付く）
- **`ok` は1つの状態だけを書く。** 「正しく動く」「適切に表示される」は禁止。
  user が画面を見て○×を即答できる文にする（札の文言・色・数字・位置）
- **`ng` は "壊れているように見えるが正常" を先回りする欄。**
  仕様どおりなのに不具合に見えるものがあれば、必ずここに書く
- **専門語を使わない。** store / props / state / API / RLS は出さない。
  「端末に覚えます」「サーバーへ送られていません」のように、
  user から見て何が起きたかで書く
- 1項目 = 1操作。2つ以上を1項目に詰めない

## 3. 並べる順

**セクションは操作の流れ順。** 前の項目の結果が次の項目の準備になっていること。
`SHARED` の並びは「ゲスト → 設定を開く → 作品の初期値 → ダンサーを置く → …
→ 保存 → 共有」で、これは実際に人が触る順。新しい機能は**関係する場面に差し込む**。
末尾に足すと、そこへ辿り着くまでに前の状態が壊れていて確認できない。

**状態を消す操作（初期化・ログアウト・共有オフ）は最後のセクションへ。**

## 4. 古くなった項目を直す

新しい項目を足す前に、**触った機能の既存項目を読み直す**。

- 消した機能の項目 → 消す
- 数値が変わった（しきい値・既定値・秒数） → 書き直す。
  過去に `COMMIT_DISTANCE_RATIO` が 0.5 → 0.22 になったのに項目が
  「半分以上引いて離す」のままだった、という取りこぼしが実際にあった
- 逆になった挙動 → 書き直したうえで `ng` に
  「以前は〜でしたが、いまは〜が正しい」と残す（user は前の挙動を覚えている）

判断に迷ったら、**その項目に書いてある `ok` が現在のコードで本当に起きるか**を
実装から確かめる。確かめずに残さない。

## 5. 公開する

チェック状態は端末の localStorage に `choreon.checklist.v4.<device>` で残る。
**印は項目の `do` の文から作る**（`makeItemIds`）ので、項目を差し込んでも
並べ替えてもずれない。**ずれるのは文を書き換えた項目だけ**で、それは
「別の質問になった」ということなので失うのが正しい。
**文を書き換えたときは、その章のチェックが外れることを user へ伝える。**

絞り込みの「この端末だけ」は `markDeviceOnly` が印を付ける。
**両方の端末ぶんの台本をその場で作って、文で突き合わせている** —
相手の台本に同じ文が無い項目だけが残る（「押す/触る」のような言い換えは
潰してから比べる）。手で印を付ける必要は無いが、**文が同じなのにその端末
でしか起きない項目**（引き下げて閉じる等）には項目に `only: true` を足す。

公開は Artifact ツールで、**必ず同じ URL へ**:

```
Artifact({
  file_path: "<repo>/docs/qa-checklist.html",
  url: "https://claude.ai/code/artifact/8524fe9c-d13b-4b8d-a2f1-c929956ba100",
  favicon: "🎭✅",
  label: "<何を足したか>",
})
```

`url` を省くと**別の台本ができてしまい**、user が開いているブックマークは
古いままになる。favicon も変えない（タブのアイコンで探しているため）。

最後に、更新した内容を user へ1行で伝える。
「客席を上にする の項目を9件足しました（スマホ 05、PC 05）」のように、
**どのセクションを見ればよいか**まで言う。

## 6. user からの報告を受け取ったとき

台本の下部に「報告の文章を作る」がある。user が貼ってくるのはその出力で、
`## 気づいたこと` に項目番号・操作・メモが並んでいる。

- **メモは症状であって原因ではない。** 「下を向いたままだった」から
  実装を辿る。項目番号（`05-3` など）で `docs/qa-checklist.html` を引けば、
  何を触ったかが分かる
- `## まだチェックしていない項目` は**失敗ではない**。そこまで進んでいないだけ。
  直す対象と混ぜない
- 直したら、その不具合を捕まえる項目を台本へ足してから閉じる
