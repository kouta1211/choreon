# Choreon

ダンスの隊形を、曲に合わせて組むためのツールです。
作った隊形は URL で配れて、受け取った人はアプリを入れずにブラウザで開けます。

**本番: https://choreon.vercel.app**（登録なしで触れます）

---

## なぜ作ったか

ダンスの隊形は、いまも紙かスライドで配られています。誰がどこに立つかは書けても、
**そこへどう動くか**は書けません。矢印を足しても、次の隊形まで何秒で移動するのか、
その速さで間に合うのかは分かりません。結局、稽古場で口頭で埋めることになります。

同じ問題を解く「Choreographic」というアプリがあります。よくできていますが、
**見る側にもアプリのインストールを求めます**。振付を確認したいだけの十数人に
インストールしてもらうのは、実際にはかなり重い頼みごとです。

そこで「**作るのは作り込んだ画面で、見るのは URL 1本で**」という形を考えました。
これがこのプロダクトの出発点であり、いまも変えていない唯一の芯です。

---

## 何ができるか

- 舞台を真上から見た図に、ダンサーを置いて動かす（吸着・回転・自由曲線の導線）
- シーンを**曲の時刻**の上に並べる。コマの間隔がそのまま移動にかけられる時間になる
- 曲を読み込んで通し再生。メトロノームと予備拍（5,6,7,8 と数えるあれ）つき
- **顔被り**（前の人に隠れる）と**速すぎる移動**（3.5 m/s 超）を自動で警告
- 隊形テンプレート59種（V字・2列・アーチなど、人数に応じて自動配置）
- 10種のテーマ（暗い系5・紙や方眼などの素材系5）
- **共有リンク**。受け取った人は自分の名前を選ぶと、自分の道順だけが
  「下手前へ 約6歩」と**言葉で**並ぶ

座標ではなく歩数と方向で出すのは、稽古場で読むものだからです。
「(3.0, 6.0) から (7.0, 2.0) へ」を頭の中で差分に直すのは、その場では手間が多すぎます。

## 開発の記録

ここからは、何を作ったかではなく**何を決めたか**の記録です。
2026年8月5日から17日までの12日間、282コミット。

### フェーズ1 — 競合の弱点を、自分の課題と重ねる

最初にやったのは機能表の比較ではなく、「**誰が困っているか**」の切り分けでした。

振付を**作る**人は1人か2人で、その人たちはアプリを入れる動機があります。
振付を**見る**人は十数人いて、その人たちには動機がありません。
競合はこの2つを同じ扱いにしていて、そこが唯一はっきりした隙でした。

だから最初から「作る側」と「見る側」を別の画面として設計しました。
見る側は編集の機能を1つも持ちません。あとで気づいたのですが、
これは使い勝手の話だけではありませんでした（フェーズ5で書きます）。

### フェーズ2 — AI を使って、2週間でコアを作り切る

Claude Code を全面的に使い、普通なら数か月かかる範囲を12日で通しました。
ただ「速く書けた」より、**速さのぶんを何に使ったか**の方が大事だと思っています。

浮いた時間は、機能を増やすのではなく**判断をコードに残すこと**に使いました。
このリポジトリのコメントは、動作の説明ではなく**なぜそうしたか**が書いてあります。

```ts
// 中身が前回と同じなら何も書き換えない(空オブジェクトを返す=状態は不変)。
// これはドラッグ中に毎pointermoveごとに呼ばれるため、素直に
// set({ dragSnapLine: line })にすると、スナップしていない間も毎回
// 新しい{x: null, y: null}オブジェクトが入り、参照が変わるせいで
// これを購読しているStageが指を動かすたびに再レンダーされてしまう
```

技術的に踏み込んだのは、この3つです。

**状態を2つに分けた** — 作品そのもの（`useProjectStore`）と、
画面の状態（`useUIStore`）。選んでいるシーンや開いているシートは保存されるべき
ではないので、置き場から分けています。

**楽観的更新を、失敗の戻し方まで含めて型にした** — 先に画面へ出し、保存し、
失敗したら**元へ戻して知らせる**。稽古場は電波が悪く、
「動かしたのに保存されていない」が最も困る壊れ方だからです。黙って飲み込む
`catch` はこのリポジトリに1つもありません。

**元に戻す／やり直しは、保存が通ってから積む** — 戻せるのは保存された変更だけ、
という約束にしました。ここは実際に一度間違えていて、それは後述します。

### フェーズ3 — インフラの壁

12日目、React Native（Expo）版に着手しました。同じロジックで
iOS/Android アプリを出せれば、という判断です。

移植そのものは進みました。純粋な計算（隊形の並べ方、秒の配り方、顔被りの判定など）
**31ファイルをバイト単位で同一に保ち、ずれたら落ちるテスト**を書いて、
Web 版との二重管理を検出できるようにしました。

止まったのは、コードではなく環境でした。

- 手元の iPhone の Expo Go が **SDK 54** までしか対応せず、プロジェクトは **SDK 57**
- iOS を最新（26.6）にしても解決しない。Expo Go 側の制約だった
- 実機に入れるには **Apple Developer Program（年 $99）** が必要
- 実機で確認できないまま、実機でしか出ない不具合（消音スイッチ、キーボード、
  画面回転）を直し続けることになる

### フェーズ4 — 下げない、という判断

選択肢は3つありました。

| | 内容 | 判断 |
|---|---|---|
| A | プロジェクトを SDK 54 へ下げる | **却下** |
| B | $99 払って実機で確認する | 保留 |
| C | Web（PWA）を先に完成させて出す | **採用** |

A を却下した理由を、印象ではなく調べてから決めました。SDK 54 は
React Native 0.86 → 0.81 まで戻ります。ファイルを扱う API（`new File(Paths.document, …)`）
は SDK 55 以降のもので書き直し、起動アニメーションが使う `react-native-worklets` は
その世代に存在しません。

決め手はそこではありませんでした。

> **書き直した結果を確かめる手段（実機）が無いまま、土台を大量に書き換えることになる。**

実機が使えないから下げるのに、下げた結果を実機で確認できない。
そのあと何かおかしくなっても、元の不具合か下げたせいかを切り分けられません。
これは技術的負債というより、**判断できない状態を自分で作る**ことだと考えて外しました。

C を選んだのは、消去法ではありません。もともとの芯が
「**見るのは URL 1本で**」だったので、Web こそがこのプロダクトの本体でした。
ネイティブは「あればなお良い」であって、なくても価値は成立します。
壁にぶつかって初めて、優先順位が元からはっきりしていたことに気づいた形です。

Expo 版は `choreon-app/` に**そのまま残してあります**。動く状態で止めてあり、
テストも539件通ります。消さないのは、この判断の記録がコードと結びついている方が
正確だからです。

### フェーズ5 — 見つけた不具合のうち、質の悪かったもの

最後に、自分で見つけて直したもののうち「気づきにくかった」順に3つ。
**動かしていても分からない壊れ方**という共通点があります。

**元に戻すが、画面だけ戻していた**
移動は保存されるのに、戻したことは保存されない。つまり
**間違えて動かしたものを元に戻して、直ったように見えたまま、間違った位置の方が
サーバーに残る**。次に開くと戻っていて、そのときには履歴も消えています。
「まだ書き込みを通していないので失敗しようがない」というコメントが残っていて、
周りが保存するようになったのにそこだけ取り残されていました。

**読むだけの画面で、読んでいる人が隊形を壊せた**
共有リンクを開いた人が、指でダンサーを動かせました。サーバーには書かれませんが、
画面の図は変わり、戻す手段がありません。袖で自分の位置を確かめている人が、
親指で誰かをずらしたまま間違った図を読むことになります。
フェーズ1で「見る側は編集機能を持たない」と決めていたのに、
実装では同じ部品を使い回して**隠していただけ**でした。

**画面が「この端末に残ります」と約束していたのに、残っていなかった**
ゲストの下書きは毎回サンプルから作り直されていました。1時間かけて組んだ隊形が、
次に開いたら消えている。書いてあることとコードが食い違っていました。

3つとも、テストを足して固定しています。

### フェーズ6 — 「スマホでも作れる」を捨てて、作る側と見る側で端末を分ける

PWA として仕上げる過程で、**スマホの実機（ブラウザ）で作成画面を触りました**。
出てきたのは、機能の不足ではなく**土俵の問題**でした。

- ステージを横に払う操作が、ブラウザの「戻る」ジェスチャと取り合いになる
- シーンの並び替えは、指だと長押しを挟まないと一覧そのものがスクロールできない
- ダンサーの丸は指より小さい。緻密に置き直すのに、画面の狭さがそのまま効く

どれも**個別には直せます**。実際にいくつかは直しました。ただ、直し続けた先に
あるのは「ネイティブアプリと同じ操作感に、ブラウザで近づけた作成画面」です。
そこは競合（スマホで完結するアプリ）がいちばん強い土俵で、
**こちらが最後発でブラウザという不利な足場から挑む場所**でした。

そこで、UX を端末で割りました。

| | 端末 | 役 |
|---|---|---|
| 振付師（作る） | **PC / タブレットのブラウザ** | マウスと広い画面で、緻密に組む |
| メンバー（見る） | **スマホのブラウザ** | URL を叩いて、自分の道順だけ読む |

これは方針転換に見えて、**フェーズ1で決めた芯をそのまま端末に落としただけ**でした。
「作るのは作り込んだ画面で、見るのは URL 1本で」と最初に書いていたのに、
実装では作る画面まで全部の画面幅へ広げようとしていた、というのが正確なところです。

決め手は、直せるかどうかではなく**勝てる場所かどうか**でした。

> スマホでの編集を磨いても、競合の土俵で二番手になるだけ。
> PC での作りやすさは、スマホ完結のアプリが**構造的に取りに来られない**場所。

判断の結果、次を**やらないこと**に決めました。

- 作成画面の、狭い画面向けのレイアウト（畳む・タブに寄せる・下に積む）
- 作成画面の、タッチ特有の制御（払って送る、長押し始動の並び替え、
  ブラウザのジェスチャとの取り合いの回避）

**閲覧側（共有リンク・マイフォーカス）は、これまで通りスマホが第一級です。**
見るだけなら指1本で、ブラウザのジェスチャとも競合しません。
PWA・オフライン・軽さといった Web の強みも、そのまま見る側の価値として残ります。

## 技術構成

**Web（本体）**

- Next.js 16 (App Router) / React 19 / TypeScript
- Tailwind CSS 4（色・余白・文字はすべてトークン経由。10テーマは CSS 変数の差し替えだけで切り替わる）
- Zustand（作品の状態と画面の状態を別ストアに分離）
- Supabase（Auth / PostgreSQL / RLS）
- dnd-kit（ドラッグ）/ motion（シーン切り替えの補間）
- Vitest — **1167件**
- PWA（マニフェスト / Service Worker / オフライン画面）

**ネイティブ（`choreon-app/`・フェーズ4で停止）**

- Expo SDK 57 / React Native 0.86 / NativeWind
- PanResponder（Web の dnd-kit が使えないため自前）
- Jest — **539件**（うち31件は Web 版とのずれ検出）

**AI**

- Gemini（隊形の講評。API キーはサーバー側から出さず、Route Handler を挟む）

## セットアップ

```bash
npm install
npm run dev
```

[http://localhost:3000](http://localhost:3000) を開いて確認する。

### Supabaseのスキーマ

[supabase/schema.sql](supabase/schema.sql) をSQL Editorで実行する
(RLSポリシー込み)。適用後はファイル末尾の確認クエリで、GRANT状況とRLSポリシーが
意図通りであることを必ず確認すること。

このファイルが**いまのスキーマの正**で、これ1本で作り直せる。以前は
`supabase/migrations/` に「既存のDBへ後から列を足す」ためのSQLを番号順に
置いていたが、すべて適用済みになったため削除した。列を足したときは
schema.sql を書き換える。

> スキーマが古いままだと、遷移時間の変更や導線の曲線編集、曲の頭出しの保存が
> PostgRESTのエラー(`PGRST204`)で失敗する。その場合アプリは
> 「DBのスキーマが古いようです。〜」というトーストを表示する。

### 環境変数

`.env.example` をコピーして `.env.local` を作成し、Supabaseプロジェクトの
Settings > API から値を入れる(`.env.local` はgit管理対象外)。

```bash
cp .env.example .env.local
```

### Supabaseの型生成

`src/lib/supabase/database.types.ts` は現状 `supabase/schema.sql` を手で
写した暫定版。Supabaseプロジェクトを作成したら、以下でCLIから正式に生成し
上書きする(生成後、暫定版と差分がないか確認すること)。

```bash
npx supabase login
npx supabase link --project-ref <project-ref>
npx supabase gen types typescript --project-id <project-ref> > src/lib/supabase/database.types.ts
```

## npm scripts

- `npm run dev` — 開発サーバー起動
- `npm run lint` — ESLint実行
- `npm run test` / `npm run test:run` — Vitest(watch / 単発実行)
- `npm run build` — 本番ビルド
- `npm run check:docs` — ドキュメントが実在するものだけを指しているか検査
  (リンク・パス・識別子・手順書の bash に混ざった罠。**文章は静かに嘘になる**ため)
- `npm run verify` — check:docs → lint → test → build をまとめて実行

## 動作確認

`docs/qa-checklist.html` が実機確認の台本です。18章・約200項目あり、
スマホとPCで文言が切り替わります。チェック状態はブラウザに残ります。

新しく作った機能は、**コミットの前にこの台本へ足す**決めにしています。
消した機能の項目を消し忘れると「動かない」という報告が来るためです。
