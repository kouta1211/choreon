# 0003. コマンド一式は「規約が本体」。`/auto-dev` は試行中とする

- 日付: 2026-08-18
- 状態: **試行中**（採用でも見送りでもない）

## 何に困っていたか

1日で `.claude/commands/` に14個のコマンドを作った。動くことは確かめたが
（パス213件・識別子67件・埋め込んだシェル全件を実行して検証）、
**使って良いかは別の話**だった。

## どうすることにしたか

**この一式の価値はコマンドではなく `.claude/rules/` と `docs/` にある。**
コマンドを全部消してもプロジェクトはほとんど失わないが、規約を消すと全部
元に戻る。だから育てるのは規約の方。コマンドは段に分けて扱う。

| 段 | もの | 扱い |
| --- | --- | --- |
| **使う** | `.claude/rules/` `docs/` / `/qa-checklist` `/daily-maintenance` `/commit` `/wrap-up` `/analyze` `/reset` | 実績があるか、読むだけで壊せない |
| **試す** | `/spec` `/test-gen` `/test-pass` `/refactor` `/pr` | 1回ずつ小さい実作業で通してから判断 |
| **保留** | `/auto-dev` `/scaffold` | 下の条件を満たすまで常用しない |

## 選ばなかった案と、その理由

- **`/auto-dev` を常用する** … 解いている問題がボトルネックではない。
  この日いちばん時間と判断を要したのは、端末の分業を決めること・
  報告から原因を見抜くこと・**取り下げる判断**で、どれもタイピング速度の
  問題ではない。一言のアイデアから PR まで自動で走る仕組みは、
  もともと速かった所を速くして、**入力が一番効く所（仕様を決める所）から
  user を外す**
- **`/auto-dev` を消す** … 5回使えば決着がつく。使わずに置くより早い
- **コマンドをいま減らす** … どれが要らないかは、使ってみないと分からない

## これで何が制約になるか

- **`/auto-dev` を採用に切り替える条件**: 小さい追加5件に使って、
  **4件が手戻り無しでマージできたら採用**。それ以下なら `/spec` で
  止める運用に戻す
- **しばらく使って一度も打たなかったコマンドは消す。** 減らすのは負けではなく、
  残ったものの信頼度を上げる作業。**読まれないファイルは静かに嘘になる**
  （実際、保守点検の色検査は `translate-x` に誤爆したまま嘘の数字を
  報告し続けていた → [lessons_learned](../../lessons_learned.md)）
- **止まって異を唱えられることが、この仕組みの一番の産物**だった
  （`.claudeignore` が効かない / docs に数字を写すと腐る / 検査コマンドが
  誤爆している / 工程が qa-checklist を踏み越えている）。
  **完全ノーフィードバックの経路は、これを構造的に出せない。**
  `/auto-dev` の「決めたこと（確認してほしい）」は、その代替であって同等ではない
